# v2.1.0 Tenant event query

Every SDK can now read back a tenant's own ingested events, including payloads,
through one new client. This is the read side of the ingest the SDKs already
perform; until now a consumer that needed its own events had to call Custd
directly.

- New `analytics.query` operation on the tenant API —
  `POST /api/v1/analytics/query` — behind the dedicated `events.read` scope.
  Available as `client.analytics.query` in JavaScript and Python,
  `client.Analytics.Query` in Go, and `client->analytics()->query` in PHP.
- The response carries the server's own assessment of the result rather than a
  bare row list: `sources[].complete` and `sources[].fresh` say whether each
  source answered the whole request and whether its data sat inside the
  freshness window, and `timing` reports the measured lag and snapshot age.
  Callers decide how far to trust a result from those values; the SDKs do not
  substitute a confidence heuristic of their own.
- Event rows are returned as column bags taken from the underlying parquet
  schema, not a fixed shape, so a column added server-side reaches callers
  without an SDK change.
- Only the documented public fields are serialised. The service also accepts an
  internal `anonymousId` exact-subject predicate and a `countOnly` flag, but
  neither is part of its public JSON contract, so a caller cannot smuggle them
  onto the wire by passing extra properties.
- Requests are validated locally before they cost a round trip: a missing
  `date`, an unknown `source`, and more than four `labelFilters` are rejected
  client-side.

Effective-tenant authority stays server-side. The credential already names the
tenant, so no SDK call accepts a tenant slug.
