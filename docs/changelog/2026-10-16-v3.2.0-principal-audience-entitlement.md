# v3.2.0 — Per-principal audience entitlement

Status: prepared locally; publication and release-mirror verification pending.

Every core SDK now exposes Custd's per-principal audience grants, which are what a consumer uses to
give one person access to one workload without touching their access to a sibling.

- `ListPrincipalAudiences` / `listPrincipalAudiences` / `list_principal_audiences` reads an
  environment's audiences for one principal, each with `granted` and `managed`. `managed` reports
  whether the environment admits only by explicit grant; where it does not, the environment is still
  organisation-membership scoped and a grant would have no effect.
- `GrantPrincipalAudience` / `grantPrincipalAudience` / `grant_principal_audience` and the matching
  revoke admit or remove exactly one audience for exactly one principal.
- Mutations carry `{directoryId, audience, organisationId}` and require `Idempotency-Key`. They answer
  `{principalId, organisationId, audience, granted, managed}` and are idempotent and audited.
- Principals are addressed by the existing `ApplicationPrincipalTarget`, so a caller keeps using the
  same identity form as its other addressed-principal operations.
- A revoke affects only the named audience: the principal's sibling audiences and its organisation
  membership are untouched, and a caller never has to name a replacement audience.

The shared version and SDK identity constants are `3.2.0`. Consumers must use the published GitHub
release once its mirrors are verified, not a local filesystem replacement.
